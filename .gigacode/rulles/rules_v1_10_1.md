## 🏛️ Архитектурные принципы — дополнения (1.10.1)

### A86. Сообщение, опубликованное до подписчика, не теряется

**Правило:** ни одно игровое сообщение об ошибке не теряется из-за порядка «рендер → подписка».

**Правила:**

- шина хранит очередь сообщений, опубликованных до первого подписчика, и отдаёт её
  первому подписчику в порядке публикации ровно один раз;
- после доставки очередь пуста; повторная подписка (включая `StrictMode`) уже доставленные
  сообщения не повторяет;
- дедупликация A79 (одна пара «действие + текст» до успешной записи) сохраняется;
- очередь живёт **в экземпляре** шины; `window.*`, `globalThis.*` и модульные переменные
  как канал состояния запрещены (A78);
- первичное чтение статистики и подписка упорядочены так, чтобы стартовая ошибка
  (`reset`/`memory`/`skip`) дошла до игрока.

**Причина:** аудит 1.10.0 показал, что при повреждённой записи или недоступном `localStorage`
данные сбрасывались/переводились в память молча: `useMap` читал статистику в инициализаторе
`useState` до `useEffect`-подписки `App`, а `_reported` навсегда подавлял повтор.

### A87. Порт вместо обратной зависимости слоёв

**Правило:** если `data` нужно сообщить о событии наружу, вводится порт в `core`, а не
импорт из `app`.

**Правила:**

- `src/data/**` импортирует только `core` и `data`;
- интерфейс `ErrorReporter` и заголовок «Ошибка хранилища» живут в `core`
  (`src/core/error-reporting.ts`), а не в `app`;
- `StatsService` принимает `ErrorReporter | null`; `ErrorBus` из `app` реализует порт
  структурно; `createServices()` связывает их;
- `app` может импортировать `core`, `data`, `services`; `data` — только `core`/`data`;
- циклы на уровне файлов и слоёв запрещены.

**Причина:** в 1.10.0 `src/data/stats-service.ts` импортировал `STORAGE_ERROR_TITLE` и тип
`ErrorBus` из `src/app/error-bus.ts`, что нарушило A53 и создало встречную зависимость
`app → data`.

### A88. Игровые диалоги — только кастомные

**Правило:** любое игровое сообщение или подтверждение — существующая модалка на
`.modal-overlay`, включая подтверждение выхода из раунда.

**Правила:**

- `alert()`, `confirm()`, `prompt()` в `src/**` запрещены (Z6/Z39 распространяется на выход);
- подтверждение выхода — `ConfirmModal` с фиксированными текстами (TR-83/T80);
- нативные диалоги не «легализуются» подменой в тестах: тест проверяет модалку;
- второй канал показа сообщений в обход `showError` запрещён.

**Причина:** `useGame.exit()` вызывал `confirm('Выйти из игры? …')` — игровое сообщение
через нативный диалог, что запрещено с 1.1.0 и повлияло на тесты (глобальная подмена
`confirm`).

### A89. Миграция — это запись, а не побочный эффект чтения

**Правило:** выполненная миграция фиксируется в хранилище, а её лог пишется один раз.

**Правила:**

- после успешной миграции запись сохраняется (write-back) с `CONFIG.VERSION`;
- шаг логируется через `console.info` ровно один раз; загрузка актуальной записи молчит;
- при провале write-back: действие из `handleError`, сообщение игроку, игра продолжается;
  ступень в пределах экземпляра сервиса повторно не логируется;
- миграция идемпотентна: повторный `load()` не меняет данные и не пишет;
- тестовый двойник хранилища сериализует данные так же, как `localStorage` (T84.4).

**Причина:** в 1.10.0 мигрированный объект не сохранялся, `LocalStorageRepository.load()`
возвращал новый объект, и каждая загрузка v1/v2-записи заново печатала ступени
(6/3 строки вместо 2/1). Тестовый `MemoryRepository` отдавал тот же объект, поэтому
дефект не ловился.

### A90. Провал записи позиции откатывает отображение

**Правило:** A80 распространяется на позицию: если `saveTrainerIndex` не сохранил данные,
игрок не показывается на новом тренажёре.

**Правила:**

- результат `saveTrainerIndex()` проверяется вызывающим;
- при `false` отображаемый индекс остаётся прежним (до раунда), `PlayerState` не фиксирует
  победу, счёт читается из хранилища, сообщение приходит через шину (A79);
- при успехе поведение 1.10.0 сохраняется (победа закрепляет, провал на новом откатывает,
  повторная игра позицию не пишет);
- write-ahead: позиция меняется в памяти только после успешной записи.

**Причина:** `useMap.gameFinished` игнорировал `boolean` от `saveTrainerIndex`: при провале
записи игрок «уезжал» вперёд, а после F5 возвращался назад.

### A91. Дополнительный сьют к модулю — исключение A60

**Правило:** для одного модуля допускается второй сьют, если он покрывает отдельный
сценарий, а не дробит существующий.

**Правила:**

- основной сьют остаётся ≤ 200 строк, дополнительные сценарии выносятся в отдельный файл
  только когда исчерпан бюджет и фикстуры уже вынесены в `test/support/`;
- имя — `<Модуль>.<сценарий>.test.tsx`; сценарии не дублируют основные;
- исключение фиксируется в `test/README.md` с указанием, почему сьют отдельный;
- «дробить сьют ради бюджета» и удалять сценарии по-прежнему запрещено (Z42).

**Причина:** `App.test.tsx` (191 строка) и `App.map-freshness.test.tsx` — два сьюта одного
модуля; правило A60 требовало один, практика 1.10.0 — исключение без правила.

## 🔧 Технические ограничения — дополнения (1.10.1)

### T79. Контракт `ErrorReporter` и `ErrorBus`

```ts
// src/core/error-reporting.ts
export interface ErrorReporter {
    report(title: string, message: string): void;
}
export const STORAGE_ERROR_TITLE = 'Ошибка хранилища';
```

- `StatsService` принимает `ErrorReporter | null` (по умолчанию `null` — сообщения не публикуются);
- `ErrorBus` (`src/app/error-bus.ts`) реализует порт: `subscribe(listener): () => void`,
  `report(title, message)`, очередь недоставленных сообщений;
- `subscribe()` сначала отдаёт очередь (в порядке публикации), затем регистрирует слушателя;
- очередь очищается после доставки; доставленные сообщения повторно не отдаются;
- `createServices()` создаёт шину и передаёт её в `StatsService`;
- тесты используют `ErrorBus` как адаптер и проверяют доставку очереди без ручного
  `report()` после монтирования.

### T80. Контракт подтверждения выхода

- `useGame(services, { onRoundFinished, onExitToMap, onExitRequested })`;
- `onExitRequested(roundScore: number): void` — вызывается по ✕; раунд не завершается,
  запись не выполняется;
- `useGame.exit()`: звук `click` + `onExitRequested(model.roundScore)`;
- повторный ✕ при открытой модалке вторую не открывает: состояние `App` идемпотентно,
  повторный `onExitRequested` не дублирует ни окно, ни звук;
- `ConfirmModal` (`src/components/ConfirmModal.tsx`) — презентационный компонент:

```ts
export interface ConfirmModalProps {
    title: string;
    message: string;
    confirmLabel: string;
    cancelLabel: string;
    onConfirm(): void;
    onCancel(): void;
}
```

- разметка: `.modal-overlay.open > .modal > h2 + p + .btn.btn-primary + .btn.btn-secondary`;
  клик по оверлею — `onCancel`; клик по `.modal` не закрывает (как `ErrorModal`, T33);
- состояние подтверждения — локальное состояние `App` (`{ roundScore } | null`), без стора;
- тексты: «Выйти из игры?», «Заработано N очков сгорят.», «Выйти», «Остаться»;
- «Выйти» → `exitGame()` + `returnToMap()` (T82); «Остаться»/оверлей — закрыть, состояние
  раунда не меняется; звук `click` — на ✕ (в `exit()`) и на кнопках модалки, без дубля;
- тесты: модалка, «Остаться», «Выйти», отсутствие записи статистики при отмене.

### T81. Контракт миграции и лога

- `StatsSchema.migrate(data, onStep?)`:
  - `onStep(from, to)` вызывается на каждую выполненную ступень;
  - по умолчанию — `console.info('[StatsSchema] миграция', from, '→', to)`;
  - поведение и сигнатура без `onStep` не меняются (совместимость с тестами 1.10.0);
- `StatsService.load()`:
  - читает запись, мигрирует; если версия изменилась — `repo.save(migrated)` (write-back);
  - логгер экземпляра помнит уже выведенные ступени (`Set<string>`) и не повторяет их,
    если write-back не удался;
  - при провале `save` — `handleError` + сообщение через порт, игра продолжается;
  - при актуальной версии — ни записи, ни лога;
- `MemoryRepository` сериализует данные (глубокая копия через JSON) в `save`/`load`;
  сьют двойника обновляется (`toEqual` вместо `toBe`);
- тест: сериализующий репозиторий, запись v1, три `load()` → две строки лога; повторный
  `load()` после write-back → ноль; запись v3 → ноль.

### T82. Контракт единого возврата на карту

- в `App` один обработчик:

```ts
const returnToMap = useCallback(() => {
    reloadMap();
    navigate('map');
}, [reloadMap, navigate]);
```

- ✕: `exitGame(); returnToMap();`; «На карту»: `returnToMap()`; смена карты: `returnToMap()`;
- отдельных копий пары `reload()` + `navigate('map')` нет;
- порядок обязателен: чтение статистики до переключения экрана (A82);
- тесты: «Играть снова» → ✕, «На карту», смена карты — одинаковый счёт.

### T83. Контракт записи позиции

- `useMap.gameFinished(isSuccessful)`:
  - вычисляется целевой индекс: победа — вперёд, провал на новом — назад;
  - вызывается `stats.saveTrainerIndex(target)`; результат проверяется;
  - при `true` — `PlayerState` фиксируется, `setState` обновляет индекс и счёт;
  - при `false` — отображаемый индекс остаётся прежним, `PlayerState` не меняет позицию,
    счёт читается из хранилища (сообщение уже опубликовано сервисом);
  - повторная игра (`isReplay`) — ранний выход без записи (A28/T23);
- тест: репозиторий бросает на `save` → индекс в UI не изменился, счёт не «прыгнул».
