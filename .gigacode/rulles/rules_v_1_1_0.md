## 🏛️ Архитектурные принципы — дополнения

### A8. Хранение данных через Repository

Данные, которые должны **сохраняться между сессиями**, хранятся через **паттерн «Репозиторий»**.

**Структура:**

- **Абстрактный класс** — описывает контракт
- **Реализации** — конкретные хранилища
- **Сервис** — бизнес-логика работы с данными

**Обязательные реализации:**

- **Основная** — реальное хранилище
- **Тестовая** — работа в памяти

**Правила:**

- Logic и Controller **не знают**, где хранятся данные
- Они работают **только** с сервисом
- Сервис работает **только** с абстрактным репозиторием
- Конкретная реализация подставляется **при инициализации**

### A9. Разделение Model и Storage

**Model** — это **состояние в памяти**.

**Storage** — это **сериализация на диск**.

**Правила:**

- Model **не знает** о Storage
- Storage **не знает** о Model
- Между ними — **сервис**, который их связывает
- Model — plain-объект или класс с полями
- Storage — репозиторий с методами `save`, `load`, `clear`

### A10. Обработка ошибок через кастомные исключения

**Ошибки**, которые могут **ожидаться** в коде, **обязаны** быть **кастомными классами**.

**Правила:**

- Кастомные исключения наследуют `Error`
- Имя класса — **суффикс `Error`** (`StorageError`, `CorruptedDataError`)
- Базовое исключение — **родитель** для группы
- Каждое исключение имеет **понятное** имя и **поле `message`**

**Примеры:**

- Базовое — для группы (например, `StorageError`)
- Наследники — конкретные случаи (например, `QuotaExceededError`)

### A11. Централизованная обработка ошибок

**Обработка ошибок** — **централизованная** через **один** модуль (`ErrorHandler`).

**Правила:**

- `ErrorHandler` **классифицирует** ошибку
- `ErrorHandler` **возвращает** инструкцию — что делать
- `ErrorHandler` **не действует сам** — действие выполняет вызывающий
- `ErrorHandler` **логирует** системные ошибки в `console`
- Игровые ошибки → показываются **в UI**

**Формат возврата:**

- Объект с **действием** (`action`) и **сообщением для игрока** (`userMessage`)
- Возможные действия: `reset`, `skip`, `memory`, `retry`

### A12. Синхронизация памяти и диска

**Правило источника истины:** **диск** — источник истины. При **сомнении** — читаем с диска.

**Правила синхронизации:**

- После **изменения** данных — сразу **сохраняем** на диск
- При **возврате** в меню — **читаем** с диска
- **Память ≡ диск** — всегда
- Изменение памяти происходит **только** после успешного сохранения

**Порядок при сохранении:**

1. Считаем **новое** значение
2. **Пробуем** сохранить
3. Если **успех** — обновляем память
4. Если **провал** — память **не меняется**

### A13. Ограничение одной сессии

**Правило:** игра работает **в одном экземпляре**.

**Правила:**

- При попытке открыть **вторую** вкладку — блокировка
- Вторая вкладка показывает **сообщение**
- Первая вкладка **продолжает** работу
- Реализация — **на усмотрение агента**

## 🔧 Технические ограничения — дополнения

### T9. Хранение — только через Repository

- **Прямой доступ** к хранилищу **запрещён** вне репозитория
- Repository — **единственная** точка работы с хранилищем
- Ключи хранилища **префиксуются** именем приложения
- Все ошибки хранилища **обрабатываются** через `try/catch`

### T10. Работа с хранилищем — правила

- **Только** сервис работает с репозиторием
- **Только** репозиторий работает с хранилищем
- Никакой другой слой **не использует** хранилище напрямую
- Все ключи хранилища — **с префиксом** приложения
- Формат данных — **сериализуемый** (без функций, классов)

### T11. Версионирование формата данных

- Данные, хранимые между сессиями, **обязаны** содержать **поле `version`**
- При изменении формата — **инкремент** версии
- Миграции — **пошаговые**: `1 → 2 → 3 → …`
- Миграции **логируются** в `console`
- При **провале** миграции — сброс и сообщение

### T12. Стиль `try/catch`

- `try/catch` — **только** в **критичных** методах
- Критичные — те, что работают с **хранилищем** или **внешними** ресурсами
- Внутренние методы — **пробрасывают** ошибки выше
- Глобальный обработчик — **страховка** для **непредвиденных** ошибок
- Глобальный обработчик **не заменяет** локальный `try/catch`

## 🚫 Запреты — дополнения

### Z5. Запрещено в работе с хранилищем

- Обращаться к `localStorage` из View, Logic, Controller
- Хранить в `localStorage` функции, классы, DOM-узлы
- Сохранять данные без обработки ошибок
- Использовать `sessionStorage` для постоянных данных
- Хранить данные **без** поля `version`

### Z6. Запрещено в работе с ошибками

- Использовать `catch (e) {}` — пустой catch
- Подавлять ошибки без логирования
- Бросать `Error` **вместо** кастомного исключения в ожидаемых случаях
- Вызывать `alert()` / `confirm()` для игровых сообщений (только кастомное модальное)
- Использовать `window.onerror` **вместо** `try/catch`

### Z7. Запрещено в сохранении

- Сохранять **промежуточное** состояние раунда
- Сохранять **очки за раунд** до успешного завершения
- Менять память **до** успешного сохранения
- Игнорировать **провал** сохранения
- Использовать **другой** формат сериализации, кроме стандартного JSON

## ✅ Обязательства агента — дополнения

При работе с **хранением данных** агент **обязан**:

1. **Использовать** паттерн Repository
2. **Создавать** кастомные исключения для ожидаемых ошибок
3. **Обрабатывать** ошибки через `ErrorHandler`
4. **Соблюдать** принцип write-ahead при сохранении
5. **Синхронизировать** память и диск
6. **Использовать** `version` в сохраняемых данных
7. **Реализовывать** миграции при изменении формата
8. **Ограничивать** работу одной сессией
9. **Не обращаться** к хранилищу из View, Logic, Controller

При работе с **ошибками** агент **обязан**:

1. **Различать** системные и игровые ошибки
2. **Логировать** системные в `console`
3. **Показывать** игровые в UI (модальное окно)
4. **Не использовать** `alert()` / `confirm()` для игровых сообщений
5. **Классифицировать** ошибки через `ErrorHandler`
6. **Возвращать** действие и сообщение, не действовать самим
